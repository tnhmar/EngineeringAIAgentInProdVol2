\chapter{Architecting the Core Runtime}
\label{ch:core-runtime}

% ------------------------------------------------------------------
% Chapter Opening
% ------------------------------------------------------------------

Chapter~1 established the contracts: the interface catalogue, the state vocabulary,
and the six design invariants.
This chapter traces the decisions that shaped each component in the framework:
why the \texttt{Run} aggregate is the only mutable root, why the loop is sequential,
why interrupts are cooperative rather than forced, and why the model client is a
thin boundary rather than a provider wrapper.
The framework repository is the implementation reference throughout.

Section~\ref{sec:state-machine} covers the \texttt{Run} aggregate and the state
machine loop.
Section~\ref{sec:executor-service} covers scheduling and admission control.
Section~\ref{sec:interrupts} covers cooperative pause, resume, timeout, and
cancellation.
Section~\ref{sec:model-client} covers the provider-neutral model client boundary.

\section{The State Machine}
\label{sec:state-machine}
% ------------------------------------------------------------------

\subsection{The Run Aggregate}
\label{subsec:run-aggregate}

The \texttt{Run} class is the only mutable aggregate root in the framework.
Every other piece of state — step history, memory records, tool results — is either
immutable or belongs to a separate repository.
This is a deliberate constraint.
If step history were part of the aggregate, every repository load would inflate
the object proportionally to the run's age.
Separating step history into \texttt{RunRepository} keeps the hot path fast and the
aggregate boundary stable: the runtime loads a compact \texttt{Run} object, transitions
it through one state, writes one \texttt{RunStep} record, and moves on.

The architectural principle encoded in \texttt{Run} is guarded state mutation:
no state transition may happen without passing through a validation guard that
rejects illegal transitions at the point of call.
The listing below shows only the \texttt{transition()} method, which is the entire
enforcement point:

\begin{lstlisting}[language=Java,caption={Guarded transition method — \texttt{runtime/run/Run.java}},label={lst:run-transition}]
// Source: runtime/run/Run.java
public void transition(RunState next) {
    if (!isLegalTransition(state, next)) {
        throw new IllegalStateException(
            "Illegal transition: " + state + " -> " + next
        );
    }
    this.state = next;
    this.updatedAt = Instant.now();
}

private boolean isLegalTransition(RunState from, RunState to) {
    Set<RunState> legal = buildLegalTransitions().get(from);
    return legal != null && legal.contains(to);
}
\end{lstlisting}

The \texttt{MODEL\_CALL \to PLANNING} transition deserves explanation.
When the model returns a response that requires further deliberation — a
multi-step plan, a clarification request, or a tool result that changes the
reasoning context — the orchestrator transitions back to \texttt{PLANNING}
rather than directly to the next action.
This preserves the invariant that \texttt{PLANNING} is always the state in which
the agent assembles its context and decides on its next action.
\texttt{PLANNING} therefore has a dual role: it is both the entry state after
queuing and the state to which the loop returns after every model response that
does not immediately resolve to a terminal action.

\subsection{Step Record Types}
\label{subsec:step-records}

Each step in a run produces two records: one written when the step begins and one
written when it ends.
The two-record pattern allows the repository to reconstruct the agent's position
even if the process is killed between the start and end of a step: the in-progress
record identifies that a step was begun but not completed.

The framework uses a single \texttt{RunStep} record with a \texttt{state}
discriminant field rather than a seven-type sealed hierarchy.
A discriminated record is simpler to persist, query, and deserialise than a
seven-type sealed hierarchy.
The \texttt{state} field already identifies which step this is; a separate type
hierarchy adds no information and creates a schema versioning problem every time
a new state is added.

\begin{lstlisting}[language=Java,caption={Unified step record — \texttt{runtime/run/RunStep.java}},label={lst:run-step}]
// Source: runtime/run/RunStep.java
public record RunStep(
    String stepId,
    String runId,
    RunState state,
    Instant startedAt,
    Instant completedAt,
    StepStatus status
) {}
\end{lstlisting}

\subsection{Step Execution and the Core Loop}
\label{subsec:core-loop}

Unexpected errors inside a step must be wrapped into a typed failure before the
runtime acts on them.
The framework classifies unchecked exceptions as \texttt{InternalFailure}, ensuring
that even framework bugs produce a classifiable outcome rather than an uncaught
exception that escapes the run boundary.

Each state must map to exactly one executor.
In the framework that mapping is maintained inside
\texttt{DefaultAgentOrchestrator}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/DefaultAgentOrchestrator.java}},
which owns the dispatch logic and validates state coverage at construction time.

The core loop is a state-dispatch entry point: it reads the current \texttt{RunState},
routes to the appropriate handler, and writes the resulting \texttt{RunStep} and
\texttt{RunState} transition before yielding control back to the scheduler.
The excerpt below shows the dispatch entry point only:

\begin{lstlisting}[language=Java,caption={State-dispatch entry point — \texttt{orchestrator/DefaultAgentOrchestrator.java}},label={lst:dispatch}]
// Source: orchestrator/DefaultAgentOrchestrator.java
private ExecutionResult dispatch(Run run, AgentTask task) {
    return switch (run.getState()) {
        case PLANNING        -> planningHandler.handle(run, task);
        case MODEL_CALL      -> modelCallHandler.handle(run, task);
        case TOOL_EXECUTION  -> toolExecutionHandler.handle(run, task);
        case MEMORY_UPDATE   -> memoryUpdateHandler.handle(run, task);
        case RESPONDING      -> respondingHandler.handle(run, task);
        default -> throw new InternalFailure(
            "No handler for state: " + run.getState()
        );
    };
}
\end{lstlisting}

\begin{notebox}
  \textbf{What the Loop Does Not Do}

  The loop does not parse model output.
  It does not own memory policies.
  It does not know which tool to call.
  It does not embed security logic.
  It does not know whether the transport is HTTP, MCP, or A2A.
  All of those decisions live in collaborating packages —
  \texttt{orchestrator/reasoning}, \texttt{memory}, \texttt{security},
  \texttt{protocols} — that the loop invokes through narrow interfaces.
  The loop's only job is advancing state and recording evidence.
\end{notebox}

\section{Executor Service}
\label{sec:executor-service}
% ------------------------------------------------------------------

A scheduler makes two decisions: when a run is admitted, and how many runs may
advance concurrently.
Both decisions are outside the run loop itself.
The loop knows nothing about the scheduler; the scheduler knows nothing about what
happens inside a step.
This separation is what allows the admission policy to change — from a fixed
concurrency limit to a priority queue, for example — without touching the loop.

\texttt{AgentTask}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/AgentTask.java}}
is the unit of scheduled work: it carries the run identifier, the request payload,
and any metadata the scheduler needs to make an admission decision.
\texttt{AgentRunner}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/AgentRunner.java}}
is the component that submits \texttt{AgentTask} instances to the virtual-thread
executor and tracks their lifecycle.
Virtual threads make the scheduling model straightforward: each run advances on its
own virtual thread, blocking on I/O without consuming a platform thread.
The semaphore admission guard prevents runaway concurrency when the model endpoint
is slow.

The two framework types are small enough to excerpt in full:

\begin{lstlisting}[language=Java,caption={\texttt{AgentTask} — \texttt{orchestrator/AgentTask.java}},label={lst:agent-task}]
// Source: orchestrator/AgentTask.java
public record AgentTask(
    RunId runId,
    AgentRequest request,
    Instant submittedAt
) {}
\end{lstlisting}

\begin{lstlisting}[language=Java,caption={\texttt{AgentRunner} interface — \texttt{orchestrator/AgentRunner.java}},label={lst:agent-runner}]
// Source: orchestrator/AgentRunner.java
public interface AgentRunner {
    CompletableFuture<AgentResult> submit(AgentTask task);
    void shutdown();
}
\end{lstlisting}

\section{Interrupts}
\label{sec:interrupts}
% ------------------------------------------------------------------

Forced thread interruption is the wrong model for agent runs.
A run that is forcibly killed leaves its working memory, step records, and tool
side-effects in an inconsistent state.
Cooperative interruption — the run checks for a pause or cancel signal at each
state transition boundary — is the only approach compatible with deterministic
replay and clean resume semantics.

\subsection{Pause and Resume}
\label{subsec:pause-resume}

A pause signal transitions the run to \texttt{PAUSED} at the next state transition
boundary.
The run's current \texttt{RunSnapshot} is persisted through \texttt{RunRepository}
before the loop yields.
A resume signal transitions the run from \texttt{PAUSED} back to \texttt{PLANNING},
where it reassembles its context from the persisted snapshot and continues from
exactly the point at which it was paused.
No work is repeated.

\subsection{Cancellation and Timeout}
\label{subsec:cancel-timeout}

Cancellation transitions the run to \texttt{CANCELLED}.
Timeout transitions the run to \texttt{TIMED\_OUT}.
Both are terminal states: the run loop exits, all resources are released, and the
failure type is recorded in the \texttt{RunSnapshot} for downstream consumers.

The lifecycle controls are exposed through
\texttt{AgentLifecycle}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/AgentLifecycle.java}},
which is the interface that callers use to pause, resume, and cancel a run without
direct access to the run loop or the scheduler internals.

\begin{warningbox}
  Forced thread interruption is not the right model for agent runs.
  A run that is forcibly killed leaves its working memory, step records,
  and tool side-effects in an inconsistent state.
  Cooperative interruption — the run checks for a pause signal at each
  state transition boundary — is the only approach compatible with
  deterministic replay and clean resume semantics.
\end{warningbox}

\section{Model Client}
\label{sec:model-client}
% ------------------------------------------------------------------

The model client boundary is one of the most important seams in the framework.
Its purpose is to prevent any provider-specific type — OpenAI's
\texttt{ChatCompletionRequest}, Anthropic's \texttt{MessageCreateParams}, or any
other vendor SDK class — from appearing inside the runtime loop or the orchestrator.
The runtime speaks only \texttt{ModelClient}; the provider implementation
translates between the framework's vocabulary and the provider's API in the
adapter layer.

The \texttt{ModelClient} interface lives in
\texttt{modelclient/}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/modelclient/}}.
The interface declares only the method signatures: the caller passes a prompt in
the framework's vocabulary and receives a response in the framework's vocabulary.
Every provider detail lives behind the implementation.

The test double (fake model client) is architecturally as important as the real
implementation.
A \texttt{FakeModelClient} that returns a fixed or scripted response sequence allows
the full run loop to be exercised in a test that runs in under 100 milliseconds
with no network access.
The fake model client is not a test convenience — it is evidence that the model
client boundary is genuinely narrow.

\begin{tipbox}
  Write the fake before you write the real implementation.
  If the fake requires more than twenty lines, the \texttt{ModelClient} interface
  is too wide.
  A narrow interface has a narrow fake.
\end{tipbox}

\begin{takeawaybox}
  Chapter~2 implements the three mechanical components of the framework:
  the guarded state machine, the virtual-thread scheduler, and the cooperative
  interrupt handler.
  None of them contain domain logic.
  Domain logic — memory selection, tool dispatch, orchestration decisions —
  is the subject of Chapter~3.
\end{takeawaybox}
