\section{From Interfaces to Motion}
\label{sec:ch2-intro}

\begin{learningbox}
After this section you will understand why \lstinline{StateMachineRunner}
is the sole orchestrator of the \lstinline{RunState} machine and
how it delegates every substantive decision to its injected
collaborators.
\end{learningbox}

Chapter~1 established the \emph{interfaces} that govern every
behavioural decision: \lstinline{Reasoning}, \lstinline{Action},
\lstinline{Memory}, \lstinline{Perception}, and the
\lstinline{ExecutionContext} that binds them.  This chapter
describes \emph{how those interfaces are put in motion}.

The answer is \lstinline{StateMachineRunner} --- a
270-line class with a single public method,
\lstinline{run(Agent, ExecutionContext)}.  It owns no domain logic
of its own; it only drives the \lstinline{RunState} machine and
delegates every substantive decision to the injected collaborators.
Understanding its internal structure is the prerequisite for every
production concern addressed in later chapters: liveness detection,
HITL suspension, deterministic replay, and multi-tenant isolation.

\section{The State Transition Table}
\label{sec:state-transition-table}

\begin{learningbox}
After this section you will be able to enumerate every legal
\lstinline{RunState} transition, its trigger, and the event it
emits --- and explain the C4 spec fix that routes
\lstinline{DEGRADED} to \lstinline{ABORTED}.
\end{learningbox}

Table~\ref{tbl:state-transitions} enumerates every legal

\lstinline{isLive()} guard at the top of the run loop

\begin{notebox}
The C4 specification (Vol.~1, Ch.~8) states: ``There is no
transition from \lstinline{DEGRADED} directly to
\lstinline{TERMINATED} --- a degraded run must either recover or be
explicitly aborted.''  The \lstinline{DEGRADED} case in
\lstinline{StateMachineRunner.step()} calls the dedicated
\lstinline{abort()} helper, which sets \lstinline{ABORTED} rather
than \lstinline{TERMINATED}.  This resolves the
state/event contradiction where the state said
\lstinline{TERMINATED} but the event said \lstinline{RUN\_ABORTED}.
\end{notebox}

\section{The Run Loop}
\label{sec:run-loop}

\begin{learningbox}
After this section you will be able to explain why the outer
\lstinline{while} loop contains no branching logic and how any
collaborator stops the run by calling \lstinline{ctx.transitionTo()}
rather than by throwing.
\end{learningbox}

The outermost loop is intentionally minimal
(Listing~\ref{lst:run-loop}).  Every early-exit, retry, and
escalation decision lives \emph{inside} \lstinline{step()}, not
here.  That discipline keeps the loop itself readable and the exit
condition unambiguous.

\begin{lstlisting}[
  language=Java,
  caption={StateMachineRunner --- outer run loop
           (\texttt{core/StateMachineRunner.java})},
  label={lst:run-loop}]
void run(Agent agent, ExecutionContext ctx) {
    while (ctx.currentState().isLive()) {
        step(agent, ctx);
    }
}

private void step(Agent agent, ExecutionContext ctx) {
    switch (ctx.currentState()) {
        case INITIALIZED -> { /* push root goal, transitionTo VALIDATING */ }
        case VALIDATING  -> { /* check resource limits, transitionTo PLANNING */ }
        case PLANNING    -> { /* perceive, decide, validate, execute, review */ }
        case DEGRADED    -> abort(ctx, ...);  // C4 fix
        default          -> {}
    }
}
\end{lstlisting}
\githubref{com.agentframework.core.StateMachineRunner}

The \lstinline{isLive()} check on \lstinline{RunState} costs a
single equality test against three constants --- no exception path,
no flag polling.  Any collaborator that wants to stop the run calls
\lstinline{ctx.transitionTo(RunState.TERMINATED)} or
\lstinline{COMPLETED} or \lstinline{ABORTED}, and the outer loop
exits cleanly on its next iteration.

\section{INITIALIZED and VALIDATING}
\label{sec:init-validating}

\begin{learningbox}
After this section you will be able to describe the two jobs of
the \lstinline{INITIALIZED} step and explain why resource limits
are checked in \lstinline{VALIDATING} rather than inside
\lstinline{PLANNING}.
\end{learningbox}

The \lstinline{INITIALIZED} step has two jobs: guard against
delegation-depth abuse and push the root goal onto the goal stack
(Listing~\ref{lst:init-step}).

\begin{lstlisting}[
  language=Java,
  caption={INITIALIZED step --- delegation guard and root goal
           (\texttt{core/StateMachineRunner.java})},
  label={lst:init-step}]
case INITIALIZED -> {
    Task t = ctx.task();
    int maxDepth = (t.maxChainDepth() > 0) ? t.maxChainDepth() : 10;
    if (ctx.currentChainDepth() > maxDepth) {
        terminate(ctx, new TerminationReason.ResourceLimit(
            "Delegation depth " + ctx.currentChainDepth()
            + " exceeds limit " + maxDepth),
            AgentEvent.EventType.DELEGATION_DEPTH_EXCEEDED,
            Map.of("depth", ctx.currentChainDepth(),
                   "limit", maxDepth));
        return;
    }
    ctx.goalStack().push(new Goal(
        "root", null, GoalStatus.PENDING, t.instruction(),
        List.of(), taskBudget));
    ctx.transitionTo(RunState.VALIDATING);
}
\end{lstlisting}
\githubref{com.agentframework.core.StateMachineRunner}

\lstinline{VALIDATING} calls \lstinline{checkResourceLimits()}
before every cycle.  Checking limits here --- rather than inside
\lstinline{PLANNING} --- means the run can never start a new
reasoning step after any limit fires.  The four limits are cycles,
tokens, wall-clock time, and monetary budget.  All four are read
from the \lstinline{Task} value object; none are hardcoded.

\section{The PLANNING Step in Full}
\label{sec:planning-step}

\begin{learningbox}
After this section you will be able to trace the full PLANNING
sequence from stale-plan injection through perception, decision,
stuck-state check, and validation branch.
\end{learningbox}

The \lstinline{PLANNING} case is the heart of the runner.  Its
sequence is: detect a stale plan; emit \lstinline{CYCLE\_STARTED};
perceive; transition to \lstinline{MODEL\_CALL}; decide;
transition back to \lstinline{PLANNING}; check for stuck state;
validate; then branch on the validation outcome
(Listing~\ref{lst:planning-step}).

\begin{lstlisting}[
  language=Java,
  caption={PLANNING step --- perception, decision, and
           validation branch
           (\texttt{core/StateMachineRunner.java})},
  label={lst:planning-step}]
case PLANNING -> {
    if (ctx.isPlanStale()) {
        ctx.workingMemory().add(new WorkingMemoryEntry(
            UUID.randomUUID().toString(),
            "Plan correction required: " + ctx.stalenessHint(),
            WorkingMemoryTier.ACTIVE, Origin.SYSTEM, 1.0,
            Instant.now(), TaintLabel.CLEAN));
        ctx.flagPlanStale(null);
        emit(ctx, AgentEvent.EventType.PLAN_STALE, Map.of());
    }
    emit(ctx, AgentEvent.EventType.CYCLE_STARTED,
        Map.of("cycle", ctx.cycleCount()));
    Observations obs      = agent.perception().perceive(ctx);
    ctx.transitionTo(RunState.MODEL_CALL);
    Decision     decision = agent.reasoning().decide(ctx, obs);
    ctx.transitionTo(RunState.PLANNING);
    liveness.checkStuck(decision, ctx).ifPresent(reason ->
        terminate(ctx, reason,
            AgentEvent.EventType.STUCK_STATE_DETECTED, Map.of()));
    if (!ctx.currentState().isLive()) return;
    ValidationResult validation = validator.validate(decision, ctx);
    switch (validation) {
        case ValidationResult.Passed p      -> executeAndReview(...);
        case ValidationResult.NeedsCorrection nc -> flagAndRetry(...);
        case ValidationResult.Failed f      -> terminate(...);
    }
}
\end{lstlisting}
\githubref{com.agentframework.core.StateMachineRunner}

\subsection{Liveness Checks Inside PLANNING}
\label{subsec:liveness-inside-planning}

Two liveness checks bracket the action call.  The first,
\lstinline{checkStuck()}, fires \emph{before} execution: it
detects identical decisions being repeated without progress.
The second, \lstinline{checkStagnation()}, fires \emph{after}
execution: it hashes the goal stack before and after the action
and flags a run as stagnant if the hash is identical across
configurable cycle thresholds.

Both checks return \lstinline{Optional<TerminationReason>}.
Using \lstinline{Optional} rather than throwing is deliberate: it
keeps the control flow linear, avoids a catch block in the middle
of the step case, and makes the calling code self-documenting.

\section{The Two-Phase Model}
\label{sec:two-phase-model}

\begin{learningbox}
After this section you will be able to describe the execute-then-review
split and explain why taint classification must run before the
result is written to working memory.
\end{learningbox}

The name ``PLANNING'' is slightly misleading: the PLANNING
state \emph{also} performs the action, then hands off to
\lstinline{Review} for post-action processing.  This two-phase
structure --- \emph{execute-then-review} --- is a deliberate design
choice that keeps each concern in a single class.

\paragraph{Phase 1 --- Execute.}
\lstinline{StateMachineRunner} calls
\lstinline{agent.action().execute(decision, ctx)},
transitions the state to \lstinline{TOOL\_EXECUTION} beforehand
and \lstinline{MEMORY\_UPDATE} afterwards.  It has no knowledge of
what the action does internally.

\paragraph{Phase 2 --- Review.}
\lstinline{Review.step()} receives the \lstinline{ActionResult} and
performs six ordered operations: taint classification, context-window
management, goal-stack update, belief-state update, long-term
memory write-back, and termination checking.  It transitions the
context to \lstinline{COMPLETED} or \lstinline{TERMINATED} when a
termination condition is met, leaving the outer loop to exit
on the next \lstinline{isLive()} check.

\subsection{Why Taint Fires First}
\label{subsec:taint-first}

The taint classifier\marginpar{\footnotesize Vol.~1, Ch.~7} runs
\emph{before} the result is written to working memory
(Listing~\ref{lst:review-excerpt}).  This ordering guarantees that
a hostile payload cannot reach the memory store.  The cost is one
extra string scan per action; the benefit is that a
prompt-injection attempt embedded in a tool response is flagged
and emitted as \lstinline{HOSTILE\_TAINT\_DETECTED} before any
subsequent reasoning cycle can read it.

\begin{lstlisting}[
  language=Java,
  caption={Review.step() --- taint-first ordering
           (\texttt{core/Review.java})},
  label={lst:review-excerpt}]
void step(ActionResult result, Decision decision,
          Observations obs, ExecutionContext ctx,
          Agent agent) {
    // Phase 2a: classify BEFORE writing to memory
    TaintLabel taint   = classifyResultTaint(result);
    String     summary = summarize(result);
    ctx.workingMemory().add(new WorkingMemoryEntry(
        UUID.randomUUID().toString(), summary,
        WorkingMemoryTier.ACTIVE, Origin.TOOL, 0.9,
        Instant.now(), taint));
    if (taint == TaintLabel.HOSTILE) {
        events.emit(new AgentEvent(ctx.runId(), ctx.tenantId(),
            AgentEvent.EventType.HOSTILE_TAINT_DETECTED,
            Instant.now(), Map.of("summary",
                summary.substring(0, Math.min(200, summary.length())))));
    }
    // Phase 2b..2f: context window, goals, beliefs, memory, termination
    ctxManager.manage(ctx.workingMemory(), ctx.task().maxTokens());
    updateGoals(result, decision, ctx);
    updateBeliefs(result, ctx);
    // long-term write-back and termination check follow ...
}
\end{lstlisting}
\githubref{com.agentframework.core.Review}

\section{Interrupts and the StepExecutionException Design}
\label{sec:interrupt-narrative}

\begin{learningbox}
After this section you will be able to distinguish internal
interrupts (resource limits, stuck states) handled by
\lstinline{terminate()} from external interrupts (HITL,
Async\-Agent\-Runtime) that require an external snapshot holder.
\end{learningbox}

A run can be interrupted by two classes of signal: \emph{resource
limits} detected by the runner itself, and \emph{external
interrupts} that arrive while an action is in flight.

\subsection{Internal Interrupts: The \texttt{terminate()} / \texttt{abort()} Contract}
\label{subsec:internal-interrupts}

The runner exposes two private helpers:
\lstinline{terminate()} for expected, recoverable stops (resource
limits, stuck states, plan incoherence) and \lstinline{abort()}
for escalated, non-recoverable exits (the \lstinline{DEGRADED} path
described in Table~\ref{tbl:state-transitions}).

\begin{lstlisting}[
  language=Java,
  caption={terminate() and abort() --- two distinct exit
           contracts (\texttt{core/StateMachineRunner.java})},
  label={lst:terminate-abort}]
// TERMINATED: resource limits, stuck, incoherence, delegation depth
private void terminate(ExecutionContext ctx,
        TerminationReason reason,
        AgentEvent.EventType eventType,
        Map<String,Object> attrs) {
    ctx.setTerminationReason(reason);
    ctx.transitionTo(RunState.TERMINATED);
    emit(ctx, eventType, attrs);
}

// ABORTED: DEGRADED escalation only.
// Spec: "a degraded run must either recover or be explicitly aborted."
private void abort(ExecutionContext ctx,
        TerminationReason reason,
        AgentEvent.EventType eventType,
        Map<String,Object> attrs) {
    ctx.setTerminationReason(reason);
    ctx.transitionTo(RunState.ABORTED);   // never TERMINATED
    emit(ctx, eventType, attrs);
}
\end{lstlisting}
\githubref{com.agentframework.core.StateMachineRunner}

Calling \lstinline{terminate()} inside \lstinline{PLANNING} does
not throw.  The next statement in the switch arm returns early,
and the outer \lstinline{while} exits on the next
\lstinline{isLive()} check.  There is no exception unwinding,
no flag race, and no possibility of a partial state transition
leaking out to callers.

\subsection{External Interrupts: HITL and AsyncAgentRuntime}
\label{subsec:external-interrupts}

When a \lstinline{Decision.Escalate} is produced by reasoning,
\lstinline{Review.step()} transitions the context to
\lstinline{TERMINATED} (not \lstinline{SUSPENDED\_HITL}).  Actual
parking at \lstinline{SUSPENDED\_HITL} is the responsibility of
\lstinline{AsyncAgentRuntime} (covered in Chapter~6), which
holds a reference to the live \lstinline{DefaultExecutionContext}
after the run and can call \lstinline{ctx.checkpoint()} to detect
and persist the suspension point.  The \lstinline{StateMachineRunner}
itself never parks --- it always runs to a terminal state and returns.

\section{What the Loop Does Not Do}
\label{sec:what-loop-does-not-do}

\begin{learningbox}
After this section you will be able to name the six concerns
that \lstinline{StateMachineRunner} explicitly refuses to own and
identify the collaborator responsible for each one.
\end{learningbox}

\begin{notebox}
\textbf{What \texttt{StateMachineRunner} deliberately does not do:}
\begin{itemize}
  \item \textbf{Scheduling.}  The runner is synchronous and
        single-threaded.  All threading lives in
        \lstinline{AgentRuntime.executeAsync()} and the injected
        \lstinline{ExecutorService}.
  \item \textbf{Serialisation.}  Snapshot creation and integrity
        hashing live in \lstinline{DefaultExecutionContext}, not
        in the runner.  The runner only calls
        \lstinline{ctx.transitionTo()} and reads
        \lstinline{ctx.currentState()}.
  \item \textbf{Memory management.}  Context-window eviction and
        working-memory limits are delegated entirely to
        \lstinline{ContextWindowManager} inside \lstinline{Review}.
  \item \textbf{Taint policy.}  The runner receives a
        \lstinline{TaintClassifier} instance; it does not compile
        patterns or define what ``hostile'' means.
  \item \textbf{Tenant policy.}  Tool-allowlist enforcement is the
        job of \lstinline{TenantPolicyEngine} inside
        \lstinline{PlanValidator} --- never of the runner.
  \item \textbf{Retry.}  There are no retry loops inside
        \lstinline{step()}.  The \lstinline{NeedsCorrection}
        path flags a stale plan and returns to
        \lstinline{VALIDATING}; the next full cycle is the retry.
\end{itemize}
\end{notebox}

This distribution of responsibility is what makes the runner
testable in isolation.  A unit test can construct a
\lstinline{StateMachineRunner} with a stub \lstinline{PlanValidator},
a no-op \lstinline{EventSink}, and a minimal \lstinline{Agent} whose
\lstinline{Reasoning} is a lambda, and exercise every transition in
Table~\ref{tbl:state-transitions} without touching a network
socket, a database, or a real language model.

\section{Replay: Re-entering the Loop from a Snapshot}
\label{sec:replay}

\begin{learningbox}
After this section you will be able to describe the three steps
of deterministic replay and explain why the integrity check must
run before any side-effecting code.
\end{learningbox}

Deterministic replay, introduced in Chapter~1 as runtime
requirement~2, is implemented in \lstinline{AgentRuntime.replay()}.
The method does three things: verify the integrity hash, build a
\lstinline{Task} from the snapshot's root goal, and construct a
fresh \lstinline{DefaultExecutionContext} restored from the
snapshot before handing it to \lstinline{StateMachineRunner}
(Listing~\ref{lst:replay-excerpt}).

\begin{lstlisting}[
  language=Java,
  caption={AgentRuntime.replay() --- snapshot verification and
           context restoration (\texttt{core/AgentRuntime.java})},
  label={lst:replay-excerpt}]
public ExecutionResult replay(
        ExecutionContext.Snapshot snapshot,
        Agent agent, String tenantId, String userId) {
    verifyIntegrity(snapshot);        // throws on hash mismatch
    Task replayTask = buildReplayTask(snapshot);
    DefaultExecutionContext ctx =
        new DefaultExecutionContext(replayTask, tenantId, userId);
    ctx.restoreFromSnapshot(snapshot);
    emit(ctx, AgentEvent.EventType.RUN_STARTED, Map.of(
        "instruction", replayTask.instruction(),
        "replayFrom",  snapshot.cycle()));
    new StateMachineRunner(validator, events).run(agent, ctx);
    emit(ctx, AgentEvent.EventType.RUN_COMPLETED,
        Map.of("state", ctx.currentState().name()));
    return ExecutionResult.from(ctx);
}
\end{lstlisting}
\githubref{com.agentframework.core.AgentRuntime}

\lstinline{verifyIntegrity()} recomputes the SHA-256 hash over all
counters in the snapshot schema and throws
\lstinline{IllegalArgumentException} if the stored hash does not
match.  A tampered or schema-mismatched snapshot is rejected
before any side-effecting code runs.

\begin{warningbox}
Always verify snapshot integrity before replay.  A snapshot that
passes the integrity check but was produced by a different schema
version must be migrated using the version adapter before replay.
The \lstinline{schemaVersion} field on
\lstinline{ExecutionContext.Snapshot} carries the version string;
checking it before calling \lstinline{replay()} is the caller's
responsibility.
\end{warningbox}

\section{Testing the Runner in Isolation}
\label{sec:testing-runner}

\begin{learningbox}
After this section you will be able to write a complete runner
unit test using only lambdas and a stub validator, with no
network, database, or live model.
\end{learningbox}

Because \lstinline{StateMachineRunner} is package-private and
accepts all collaborators through its constructor, the full state
machine can be exercised without any external infrastructure.

\begin{lstlisting}[
  language=Java,
  caption={Unit test pattern --- all transitions covered with
           lambdas and a stub validator},
  label={lst:runner-test}]
AgentRuntime runtime = new AgentRuntime(
    new PassThroughPlanValidator(),
    EventSink.noop());
Agent agent = new Agent.Builder()
    .name("test")
    .perception(ctx -> Observations.empty())
    .reasoning((ctx, obs) -> Decision.finalAnswer("done"))
    .action((dec, ctx) -> ActionResult.success(ToolResult.of("ok")))
    .memory(MemoryAdapter.noop())
    .build();
Task task = Task.builder()
    .instruction("test")
    .maxCycles(5)
    .maxTokens(10_000)
    .build();
ExecutionResult result = runtime.execute(agent, task);
assertEquals(RunState.COMPLETED, result.finalState());
\end{lstlisting}

\begin{tipbox}
Use \lstinline{EventSink.capturing()} instead of
\lstinline{EventSink.noop()} to assert that specific events were
emitted in the correct order.  This is the preferred way to
verify the event taxonomy from Chapter~1 in integration tests.
\end{tipbox}

\begin{takeawaybox}{Chapter 2 Takeaways}
\lstinline{StateMachineRunner} is a pure orchestrator: it drives
the \lstinline{RunState} machine through a single
\lstinline{while~(isLive())} loop and delegates every domain
decision---scheduling, serialisation, taint, tenant policy, and
retry---to six injected collaborators, making the entire runtime
testable with lambdas and a stub validator.
The two-phase execute-then-review model, the
\lstinline{DEGRADED}\,\textrightarrow\,\lstinline{ABORTED} C4 fix,
and the pre-write taint check are the three design decisions that
distinguish a production-grade loop from a na\"ive one.
\end{takeawaybox}
