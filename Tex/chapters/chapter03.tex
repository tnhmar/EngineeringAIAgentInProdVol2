\section{The Domain Layer: What the Runtime Delegates}
\label{sec:domain-layer}

The runtime loop owns state transitions and event emission.
It delegates all domain decisions to three subsystems: memory (what context the
model sees), tools (what actions the agent takes), and orchestration (how model
output maps to the next action).
The loop never makes a domain decision itself — it calls through narrow interfaces
and records the outcome.

The memory tier requires careful architecture because different kinds of memory have
different lifetimes, different storage requirements, and different query patterns.
\textbf{Working memory} is run-scoped and in-process: it holds the conversation
turns and intermediate tool results that are relevant to the current run, and it
is discarded when the run ends.
\textbf{Durable memory} covers the tiers that survive across runs — episodic
(per-agent experience records), semantic (cross-agent queryable knowledge), and
procedural (reusable task patterns).
The previous volume conflated these into a single \texttt{MemoryStore} interface.
The framework separates them into distinct sub-packages under \texttt{memory/}.

\begin{table}[h]
\centering
\caption{Memory tier architecture — scope, persistence, and framework package}
\label{tab:memory-tiers}
\begin{tabular}{llll}
\toprule
\textbf{Memory tier} & \textbf{Scope} & \textbf{Persisted} & \textbf{Framework package} \\
\midrule
Working    & Single run, in-process & No  & \texttt{memory/working} \\
Episodic   & Cross-run, per-agent   & Yes & \texttt{memory/episodic} \\
Semantic   & Cross-agent, queryable & Yes & \texttt{memory/semantic} \\
Procedural & Reusable task patterns & Yes & \texttt{memory/procedural} \\
\bottomrule
\end{tabular}
\end{table}

\section{Memory}
\label{sec:memory}
% ------------------------------------------------------------------

The runtime does not choose a memory backend.
It calls \texttt{MemoryStore}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/memory/}},
which is a narrow interface.
The backend — in-memory, Redis, PostgreSQL, or a vector store — is wired at
construction time through the builder.
This is the inward-dependency invariant applied to memory: the runtime core
never imports a Redis type, a JDBC driver class, or a vector store SDK.

For working memory, the framework provides
\texttt{WorkingMemoryStore}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/memory/working/WorkingMemoryStore.java}}
— a bounded, run-scoped scratchpad that lives in-process for the duration of a
single run.
It exposes only the operations the runtime needs: put a keyed value, get by key,
and take an immutable snapshot for context assembly.

\begin{lstlisting}[language=Java,caption={Working-memory scratchpad — \texttt{memory/working/WorkingMemoryStore.java}},label={lst:working-memory}]
// Source: memory/working/WorkingMemoryStore.java
public class WorkingMemoryStore {

    private volatile ConcurrentHashMap<String, Object> store = new ConcurrentHashMap<>();

    public void put(String key, Object value) {
        Objects.requireNonNull(key, "key must not be null");
        store.put(key, value);
    }

    public Optional<Object> get(String key) {
        return Optional.ofNullable(store.get(key));
    }

    public void remove(String key) { store.remove(key); }

    /** Atomically replaces the entire map — safe under concurrent writes. */
    public void clear() { store = new ConcurrentHashMap<>(); }

    public Map<String, Object> snapshot() { return Collections.unmodifiableMap(store); }
    public int size() { return store.size(); }
}
\end{lstlisting}

For durable memory tiers the framework differentiates between tiers at the type level
through distinct interfaces and package structures under
\texttt{memory/}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/memory/}}.
A \texttt{MemoryPolicy} governs which records are selected for the model's context
window and when records are retired.
The orchestrator calls \texttt{MemoryPolicy} to decide what to pass to the model;
it never inspects the backing store directly.

\begin{notebox}
  The wiring diagram is simple: the builder connects a \texttt{MemoryStore}
  implementation to the \texttt{MemoryPolicy} consumer at construction time.
  From the runtime's perspective there is one interface and one policy.
  The backend topology — one store or many, local or remote — is an
  infrastructure decision that does not touch the core.
\end{notebox}

\section{Tool Registry and Execution}
\label{sec:tools}
% ------------------------------------------------------------------

A tool is a typed function: it accepts a typed input, produces a typed output, and
declares a typed failure mode.
The registry separates \emph{discovery} (listing available tools and their
descriptors) from \emph{execution} (calling one tool with a concrete argument).
That separation allows the orchestrator to describe available tools to the model
— filling the model's context with tool names and schemas — without executing any
of them.
Tool execution happens only when the model selects a tool and the security policy
permits the call.

The \texttt{ToolRegistry} class lives in
\texttt{tooling/registry/}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/tooling/registry/ToolRegistry.java}}.
It maintains a concurrent map of \texttt{ToolDefinition} entries keyed by tool
identifier, and exposes register, find, list-by-category, and deregister operations.

\begin{lstlisting}[language=Java,caption={\texttt{ToolRegistry} — \texttt{tooling/registry/ToolRegistry.java}},label={lst:tool-registry}]
// Source: tooling/registry/ToolRegistry.java
public class ToolRegistry {
    private final Map<String, ToolDefinition> tools = new ConcurrentHashMap<>();

    public void register(ToolDefinition tool)    { tools.put(tool.toolId(), tool); }
    public Optional<ToolDefinition> find(String toolId) {
        return Optional.ofNullable(tools.get(toolId));
    }
    public List<ToolDefinition> byCategory(ToolCategory category) {
        return tools.values().stream()
                    .filter(t -> t.category() == category).toList();
    }
    public List<ToolDefinition> all()            { return List.copyOf(tools.values()); }
    public void deregister(String toolId)        { tools.remove(toolId); }

    /** Factory: returns an empty registry (no tools registered). */
    public static ToolRegistry empty()           { return new ToolRegistry(); }
}
\end{lstlisting}

The architectural point the listing encodes: \texttt{ToolRegistry} holds
\texttt{ToolDefinition} descriptors, not callables.
The orchestrator queries \texttt{all()} to build the tool list it sends to the
model; the model selects a tool by \texttt{toolId}; the orchestrator calls
\texttt{find(toolId)} and then dispatches execution separately.
Discovery and execution are two distinct operations on two distinct types.

\subsection{Parallel Tool Execution}
\label{subsec:parallel-tools}

When the model requests multiple tool calls in a single response, the framework
dispatches them through \texttt{AgentDelegate}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/AgentDelegate.java}}.
The delegation interface is the same whether the peer agent is in-process or remote,
which means the orchestrator does not change its dispatch logic based on topology.
The same \texttt{AgentDelegate} abstraction is also used for sub-agent delegation
in Chapter~4's A2A section.

\subsection{Remote Tools via MCP}
\label{subsec:mcp-tool-adapter}

MCP (Model Context Protocol) tools are remote tools that look local from inside the
framework.
An MCP tool adapter implements the \texttt{Tool} interface but delegates execution
to a remote MCP server over the protocol wire.
From the \texttt{ToolRegistry}'s perspective there is no distinction: every entry
in the registry is a \texttt{ToolDefinition}, regardless of where the execution happens.
The adapter wires the transport; the registry and the orchestrator use the same
interface in either case.
The adapter lives in
\texttt{protocols/}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/protocols/}}.

\section{Orchestration}
\label{sec:orchestrator}
% ------------------------------------------------------------------

The orchestrator translates model output into a declared next action.
It does not execute tools, write memory, or send responses.
It decides.

The orchestrator pipeline inside the framework is not a fixed ReAct loop.
It is a set of composable stages:

\begin{enumerate}
  \item \textbf{Perception} \texttt{(orchestrator/perception/)} — assembles the
        observable state from memory, tool results, and conversation history.
  \item \textbf{Reasoning} \texttt{(orchestrator/reasoning/)} — calls the model
        and interprets its output.
  \item \textbf{Action} \texttt{(orchestrator/action/)} — translates the reasoning
        output into a concrete next action (tool call, memory write, response,
        delegation).
  \item \textbf{Reflection} \texttt{(orchestrator/reflection/)} — evaluates the
        outcome of the previous action and updates the run's self-assessment.
  \item \textbf{Termination} \texttt{(orchestrator/termination/)} — evaluates
        stop conditions including hard step limits, goal satisfaction, and
        external signals.
  \item \textbf{Failure detection} \texttt{(orchestrator/failuredetection/)} —
        a cross-cutting concern that classifies any exception raised during
        pipeline execution into the framework's typed failure hierarchy.
\end{enumerate}

The decision dispatch section of
\texttt{DefaultAgentOrchestrator}\footnote{\url{https://github.com/tnhmar/agent-framework/blob/main/src/main/java/com/agentruntime/orchestrator/DefaultAgentOrchestrator.java}}
routes the current \texttt{AgentTask} through the pipeline stages in sequence.
The excerpt below shows the pipeline invocation structure:

\begin{lstlisting}[language=Java,caption={Pipeline invocation in \texttt{orchestrator/DefaultAgentOrchestrator.java}},label={lst:pipeline}]
// Source: orchestrator/DefaultAgentOrchestrator.java
private NextAction runPipeline(Run run, AgentTask task) {
    var percept   = perception.perceive(run, task);
    var reasoning = reasoner.reason(percept);
    var action    = actionSelector.select(reasoning);
    reflection.reflect(run, action);
    if (termination.shouldTerminate(run, action)) {
        return NextAction.terminate(action);
    }
    return action;
}
\end{lstlisting}

\begin{tipbox}
  The orchestrator pipeline is not a fixed ReAct loop.
  It is a set of composable stages that can be extended or replaced.
  The perception stage can be enriched with retrieval.
  The reasoning stage can be swapped for a plan-and-execute strategy.
  The termination stage can enforce hard step limits.
  The framework's \texttt{DefaultAgentOrchestrator} provides a working
  baseline; production deployments often extend individual stages.
\end{tipbox}

\begin{takeawaybox}
  Chapter~3 implements the three domain subsystems: the memory tier, the tool
  registry, and the orchestration pipeline.
  Each subsystem is reachable from the runtime loop through a narrow interface.
  The implementations are wired at construction time through the builder;
  they do not call back into the runtime loop.
  Chapter~4 adds the protocol edge — the adapters that make the runtime
  reachable from the outside world.
\end{takeawaybox}
