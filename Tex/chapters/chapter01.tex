\chapter{Design Principles Before Writing Code}
\label{ch:design-principles-before-writing-code}
\chapterquote{A well-designed system makes the correct path
the easiest path.}{Adapted from production engineering practice}

This chapter defines the architectural contract for the Java agent
framework built across this part of the book.
It does not implement anything.
Its job is to establish the abstractions, boundaries, state model,
and quality rules that
Chapters~\ref{ch:core-runtime} through~\ref{ch:protocol-stack}
must obey --- and to give the reader a stable reference to check
any later implementation decision against.

Section~\ref{sec:runtime-requirements-recap} translates the
conceptual agent loop from Volume~1 into concrete runtime
responsibilities.
Section~\ref{sec:testability-and-observability} establishes
testability and observability as first-class design properties.
Section~\ref{sec:java-concurrency-models} selects and justifies a
Java~25 concurrency model for the agent loop.
Section~\ref{sec:dependency-injection-and-modularity} defines the
full interface catalogue, the core domain model, and the builder
that assembles a valid runtime from those parts.
Section~\ref{sec:run-first-call-to-final-state} traces a complete
run from first call to final state, mapping every state transition
to the contracts and principles introduced in this chapter.
Section~\ref{sec:before-you-ship} closes with a verification
checklist that maps each principle to a concrete, testable
criterion.

What this chapter deliberately does not do: it does not build the
state machine, wire the model client, implement memory backends, or
add protocol support.
Each of those belongs to the chapter whose scope owns it.

\section{Recap of Runtime Requirements from Volume~1}
\label{sec:runtime-requirements-recap}

\begin{learningbox}
By the end of this section, you will be able to map the conceptual
agent loop from Volume~1 to concrete runtime responsibilities,
identify which responsibilities belong in the core framework, and
trace each requirement back to the failure mode it prevents.
\end{learningbox}

Volume~1 established that an agent is a stateful software system
that repeatedly observes input, reasons over context, invokes
actions, records outcomes, and decides whether to continue.
The Perceive--Reason--Act--Reflect cycle described there was a
conceptual model.\marginpar{\footnotesize\itshape See Vol.~1 Ch.~3:
The Agentic Loop}
In this part, that cycle becomes a Java runtime with explicit
contracts, deterministic control flow, and observable execution
boundaries.

The key shift from Volume~1 to this part is one of
\emph{responsibility}.
Volume~1 described what an agent does.
This part defines who owns what.
The answer is consistent throughout: the \component{AgentRuntime}
owns the loop.
The model client, tool layer, memory system, and protocol adapters
are dependencies inside that loop --- not alternatives to it.

\subsection*{The failure modes that motivate the requirements}
\label{subsec:failure-modes-ch1}

Before listing the six requirements, it is worth being concrete
about what happens when production teams build agent systems
without them.
These are not hypothetical risks; they are patterns that recur
across teams shipping agents for the first time.

\textbf{Hidden state in local variables.}
The most common structural mistake is to let run state live in
local variables inside a method that calls the model in a loop.
The loop works in a demo.
It breaks in production when a tool call times out, when the
process restarts mid-run, or when an operator needs to inspect
what the agent was doing at the moment it produced an unexpected
result.
There is no state to inspect because there is no persistent state
--- only a stack frame that no longer exists.
Requirement~1 (explicit state) directly prevents this failure.

\textbf{The model API as the architecture.}
When engineers start from a model provider SDK and build outward,
the codebase organises itself around request payloads and ad hoc
callback chains.
Planning logic, tool dispatch, memory loading, and response
formatting all accumulate inside a single function that calls the
model.
The function grows until it cannot be tested without a live API
key, cannot be debugged without reading several hundred lines of
interleaved concerns, and cannot be extended without breaking
something already working.
Requirements~2 and~3 --- narrow contracts and inward dependency
--- prevent this by separating planning, model invocation, tool
execution, memory updates, and response emission behind small
interfaces that can evolve independently.

\textbf{Silent tool errors.}
When tools fail silently --- returning an empty result, logging a
warning, and continuing --- the model receives bad evidence on the
next turn.
The agent may hallucinate a result or loop indefinitely trying to
recover from a failure it cannot see.
Requirement~5 (typed failures) forces every failure to be
classified and surfaced to the runtime, which can then make a
policy decision: retry, escalate, or terminate.

\textbf{The ``black box'' run.}
Without structured execution records, the only evidence of what
an agent did is whatever it printed to a log file.
Post-mortem analysis becomes an exercise in reconstructing intent
from unstructured text.
Requirement~4 (observable steps) makes every state transition
produce durable, structured evidence that tracing systems,
replay tools, and human operators can all consume directly.

\textbf{Tests that require production infrastructure.}
A framework that cannot be tested without a running model
provider, a live Redis cluster, and a deployed database is a
framework that will not be tested thoroughly.
The test cycle becomes too slow and too brittle to sustain.
Requirement~6 (testability first) means that every external
dependency --- model provider, tool executor, memory backend,
event bus --- is injectable, and the framework ships with
in-memory fakes for all of them.

The runtime in this part must satisfy six core requirements:

\begin{enumerate}
  \item It must represent execution state explicitly rather than
        hiding it in local variables or prompt text.
  \item It must separate planning, model invocation, tool
        execution, memory updates, and response emission into
        narrow contracts.
  \item It must allow infrastructure and domain dependencies to
        be injected at the edges.
  \item It must emit enough structured events to make each step
        replayable and diagnosable.
  \item It must classify failures into typed categories that the
        runtime can reason about.
  \item It must remain easy to test with fake model clients, fake
        tools, in-memory repositories, and deterministic clocks.
\end{enumerate}

These requirements are not stylistic preferences.
They are engineering constraints derived directly from the failure
modes described above.
Requirements~1 and~5 drive Chapter~\ref{ch:core-runtime}'s state
machine design and typed failure handling.
Requirements~3 and~6 drive the interface boundaries and builder
pattern in Section~\ref{sec:dependency-injection-and-modularity}.
Requirements~2 and~4 drive
Chapter~\ref{ch:memory-tools-orchestration}'s orchestrator, tool,
and memory contracts, and
Chapter~\ref{ch:protocol-stack}'s protocol separation.

\begin{notebox}
This chapter defines interfaces before implementations.
That ordering is deliberate.
In a framework, implementation must conform to architecture.
Establishing the contracts first prevents later code from quietly
redefining the boundaries.
\end{notebox}

\begin{takeawaybox}
Every design decision in
Chapters~\ref{ch:core-runtime} through~\ref{ch:protocol-stack}
should be traceable to one of the six runtime requirements.
If a proposed implementation cannot be justified by one of them,
treat it as scope creep rather than a feature.
\end{takeawaybox}

\section{Designing for Testability and Observability}
\label{sec:testability-and-observability}

\begin{learningbox}
By the end of this section, you will be able to explain why
testability and observability are architectural properties rather
than after-the-fact additions, describe the three levels of
observable evidence a production runtime must produce, and
identify which interfaces enforce each property.
\end{learningbox}

A framework becomes hard to operate long before it becomes hard
to extend.
The first serious production failure is rarely ``we could not add
a feature.''
It is ``we could not tell what the agent did, why it did it, or
where it got stuck.''
For that reason, \term{testability} and \term{observability} must
be treated as first-class design goals before any runtime loop is
written.

\subsection{Why observability cannot be bolted on}
\label{subsec:why-observability-cannot-be-bolted-on}

Consider a common failure pattern.
A team ships an agent that works well in staging.
In production, a specific class of user request causes the agent
to produce a final answer that is factually wrong.
The team checks the logs and finds a sequence of model responses
interspersed with tool call outputs.
They cannot tell whether the wrong answer came from a bad tool
result, from a model hallucination on top of a correct tool
result, from a planning step that chose the wrong tool entirely,
or from a memory retrieval that injected stale context.
The logs are output, not evidence.
They record what happened, not why.

The team responds by adding more log statements.
This is the wrong fix.
More log statements produce more output without adding causal
structure.
The correct fix is to ensure that every state transition produces
a durable, typed record that directly answers the questions:
which state was entered, what input did the step receive, what
output did it produce, how long did it take, and what failure
category was assigned if it failed.
Those are not log statements --- they are \term{execution records},
and they must be designed into the framework from the start.

The same argument applies to testability.
A test that calls the full runtime with a real model provider is
not a unit test --- it is an integration test with non-deterministic
inputs.
It may pass today because the model produces a sensible response,
and fail tomorrow because the model's behaviour changed.
The framework must allow every component to be replaced with a
controlled fake so that a test can assert precise behavioural
invariants without depending on external services.
This requires that every external dependency is injectable from the
outside, not constructed internally.

If a later implementation introduces direct framework knowledge

here.
The right response is to fix the implementation, not to relax
the principle.

\begin{warningbox}
A common anti-pattern is to add observability after the runtime
already works.
That usually produces verbose logging without causal structure.
Observable systems do not start with more log lines --- they start
with better execution models.
Structuring events around state transitions rather than around log
statements is the foundation.
\end{warningbox}

\subsection{What to make observable}
\label{subsec:what-to-make-observable}

The framework should expose observability at three levels.

\begin{enumerate}
  \item \term{Run-level visibility}: when a run starts, ends,
        pauses, resumes, times out, or fails.
  \item \term{Step-level visibility}: which executor ran, what
        state it handled, how long it took, and what transition
        it produced.
  \item \term{Dependency-level visibility}: model latency, tool
        latency, retrieval volume, and external failure
        categories.
\end{enumerate}

That hierarchy prevents the failure common in early agent
frameworks where everything is either a raw log line or a final
answer.
A serious runtime needs a middle layer of step evidence.
To make this concrete: when a tool call fails, the runtime should
produce a typed \component{ToolFailure}, a completed step record
with duration and input fingerprint, and a
\component{StepCompletedEvent} emitted to subscribers.
That three-part evidence trail is what enables the replay,
explainability, and debugging capabilities that Volume~2 Part~3
covers in depth.\marginpar{\footnotesize\itshape Vol.~2 Part~3:
Observability \& Replay}

\begin{tipbox}
If a test cannot assert which state transition occurred, the
runtime is too implicit.
If an operator cannot identify which step failed from structured
events alone, the runtime is under-instrumented.
Both are design problems --- they cannot be patched cleanly after
the fact.
\end{tipbox}

In practical terms, testability means the framework must make
side effects replaceable.
Every external dependency --- model provider, tool executor,
memory backend, event bus --- must be injectable.
Observability means every state transition must produce durable
evidence: a stable \component{RunId}, timestamped step records,
and structured events capable of feeding tracing, metrics,
logging, and replay infrastructure.

\begin{takeawaybox}
Testability and observability shape interface design.
They are not bolt-on concerns.
They determine whether the framework can be trusted in production,
debugged under pressure, and replayed for post-mortem analysis.
Any interface that hides its side effects or produces no record of
its execution works against both properties.
\end{takeawaybox}

\section{Java Concurrency Models for Agent Loops}
\label{sec:java-concurrency-models}

\begin{learningbox}
By the end of this section, you will be able to choose a
Java~25 concurrency model appropriate for this framework, justify
why a sequential per-run state machine is safer than speculative
async chains, and identify where structured concurrency is the
right tool for explicit parallelism.
\end{learningbox}

The implementation target for this part is Java~25 LTS.
That platform provides a stable, modern foundation without
requiring preview flags.
The language and runtime features directly relevant to this
framework are:

\begin{itemize}
  \item \term{Records}: immutable value types for state snapshots,
        step outcomes, domain identifiers, and domain events ---
        eliminating the ceremony of hand-written value classes.
  \item \term{Sealed interfaces}: closed type hierarchies for
        failure variants and action types --- allowing the
        compiler to enforce exhaustive dispatch.
  \item \term{Pattern matching in switch} (finalised in
        Java~25): clean, cast-free dispatch over sealed types
        throughout the runtime loop.
  \item \term{Virtual threads} (stable since Java~21, default in
        Java~25): the framework handles thousands of concurrent
        runs without thread pool tuning or callback-based async
        code.
  \item \term{Structured concurrency} (finalised in Java~25):
        when the framework opts into parallelism --- for example,
        parallel tool execution --- sub-tasks fail together as a
        cancellable unit and do not leak threads silently.
\end{itemize}

\subsection{Why async chains are the wrong model here}
\label{subsec:why-async-chains-wrong}

The reactive and async programming models are powerful, but they
are the wrong default for a framework whose primary goal is
correctness and debuggability.
Consider what happens when an agent run is modelled as a chain of
\code{CompletableFuture} stages: planning stage, model call stage,
tool execution stage, memory update stage.
Each stage hands off to the next via a callback.
When a tool call fails halfway through a multi-tool execution, the
failure propagates through a chain of anonymous lambdas.
Stack traces become nearly unreadable.
The state of the run at the moment of failure is implicit ---
spread across the closure variables captured by each lambda.
Replay requires reconstructing the chain from scratch rather than
resuming from a named state.
Cancellation must be threaded manually through every callback to
ensure that no continuation runs after a cancel request.

None of these problems are unsolvable, but they all add
complexity that compounds as the framework grows.
A sequential state machine does not have these problems by
default.
State is explicit and named.
Failures are caught at a single dispatch point and classified
before propagating.
Cancellation is a flag check at the top of the loop.
Replay is a matter of loading a named state and re-executing the
executor registered for that state.
The framework adopts the sequential model and pays for the
simplicity it earns by keeping async boundaries explicit and
intentional.

\subsection{Concurrency options and trade-offs}
\label{subsec:concurrency-options}

Agent systems are inherently concurrent at the system level.
Multiple runs may execute simultaneously.
Tool calls may block.
Model requests may be in flight at the same time.
Event consumers may subscribe to run progress while execution
continues.
But concurrency at the system boundary is not the same as
uncontrolled concurrency inside a single run.

\subsection{Why the run loop stays sequential}
\label{subsec:sequential-run-loop}

The framework adopts one governing rule: a single run advances
through its state machine in a controlled sequence; the scheduler
decides how many runs may progress concurrently.
This preserves deterministic reasoning about any individual run
while still allowing throughput across many runs.

Within a single run, speculative parallelism is avoided until
state ownership is mature.
Planning, model calls, tool outcomes, and memory writes all
mutate run context.
Concurrent mutations without strict ownership produce race
conditions that are difficult to reproduce and dangerous to fix
in production.

A sequential run loop also makes pause, resume, cancellation, and
deterministic replay more tractable.
Each transition has exactly one predecessor and one recorded
outcome.
